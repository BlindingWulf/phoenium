## Specific overlaps and policy decisions

- ScalableLux identifies itself as Starlight lineage and supplies `starlight`. Do not add Starlight beside it. C2ME's general generation scheduling is a different service; the selected pair is blocked, not proved redundant.
- FastNoise targets noise/aquifer/biome/ore/palette paths; C2ME has compiler/native-noise modules, so exact noise modules may overlap. Their whole projects are not duplicates. Structure Layout Optimizer targets jigsaw layout/intersection/template work, a separate stage. No combination benefit was inferred from descriptions.
- ViaFabric already contains ViaVersion 5.12.0-SNAPSHOT and MC26.1/26.2 support modules. An additional identical ViaVersion provider is REDUNDANT_WITH the bundled implementation and risks competing providers. ViaFabricPlus was not installed. Backwards and Rewind serve different older-client ranges; their need is a supported-client policy decision.
- ServerCore dynamic distance/mob-cap control, activation range, villager lobotomy, breeding caps and pearl chunk-loading policy change behavior. The control switches these off; the five optional optimization switches were also disabled to test whether runtime configuration removed the callback (it did not). No performance credit comes from less simulation.
- ServerCore's same-value XP merge and Clumps' heterogeneous-value merge are not fully equivalent. Stage 7 now accepts the locked Clumps 26.2.1 heterogeneous 3+7 path as a scoped result: `clumpedMap={3:1,7:1}`, total XP 10, save/restart W1/W4, real-client pickup/Mending and explicit removal all pass. Mass-farm/performance coverage remains untested.
- Panda's per-lag-area projectile limits, per-player ender-pearl limits, and mob/vehicle staggering are separate desired protections. ServerCore's all-or-nothing pearl chunk-loading switch is not a per-player cap. Activation-range skipping is not equivalent to bounded staggering. Do not silently inherit Panda defaults or source bugs: its projectile bucket lacks a world key and its removal loop repeatedly selects the first entity. Review native policy from requirements.

## Resource screen and boundaries

FerriteCore was capped at three paired `GC.class_histogram` samples after the same signal/save preparation. Control retained bytes: 157,234,120 / 157,518,800 / 157,476,664. FerriteCore: 148,913,896 / 148,996,488 / 148,945,192. Savings: 8,320,224 / 8,522,312 / 8,531,472 bytes (5.2916 / 5.4103 / 5.4176%). Mean: 8,458,003 bytes, 8.066 MiB, 5.3732%. This is a post-GC heap screen, not RSS, allocation rate, sustained MSPT or general server throughput.

Whole-process 200 ms samples and thread dumps are retained. For context, first-phase peak thread counts were 83 for the W1 API control, 88 with ScalableLux, 112 for standalone C2ME, and 84 with FastNoise. These include generation, Netty, JVM and GC services; they are not gameplay-worker counts. One C2ME global pool evaluated to 2; ScalableLux had 5 named lighting workers even in W1. A final joint executor/CPU budget was not established because the prerequisites fail.

No optimizer earns a speed claim here. Tick/queue latency, steady-state allocation, old-client translation cost, Bedrock cost and audio latency remain UNKNOWN/NOT_MEASURED. Native generation's 64 requested core chunks plus surrounding protochunks are retained, but control block-state differences preclude strict terrain parity attribution; the deterministic structure-NBT comparison is separately meaningful. Chunky's work did not finish, and its redstone phase was sequential and never reached, so simultaneous pregeneration/gameplay remains untested.
